# Properties

## Purpose
Manages the Bogineni Group's leasing units (properties/spaces) — CRUD, photo galleries, portfolio/company grouping, bulk import from Excel/PDF, and AI-extracted rental agreement documents. Called "Properties" in the nav but the underlying entity/table is `LeasingUnit` / `leasing_units`, not `Property`.

## Frontend
- **Screens**: `frontend/lib/features/properties/presentation/screens/leasing_list_screen.dart` — the ONLY screen wired into the router (`/properties` → `LeasingListScreen`). Two-level UI: Level 1 shows company/portfolio cards (grouped by `companyName`), Level 2 (after tapping a card) shows a filterable/searchable table (desktop) or card list (mobile) of units within that company.
- **Providers**: `frontend/lib/features/properties/presentation/providers/leasing_provider.dart` (`LeasingProvider`) — owns `_units` (`List<LeasingUnit>`), company grouping/summary (`CompanySummary`), status filter, search query, selected company (drill-down state), and all CRUD/import mutations. Registered where LeasingListScreen's ancestor Provider tree sets it up.
- **Repositories**: `frontend/lib/features/properties/data/repositories/leasing_repository.dart` (`LeasingRepository`) — talks **directly to Supabase** (`leasing_units` + `area_entries` tables), not the backend API, for list/insert/update/delete/deletePortfolio. Backend API is used only for photos, agreements, and PDF import (all via `ApiClient.properties` / Dio, called directly from the screen/dialog, not through this repository).
- **Key widgets/dialogs**:
  - `presentation/widgets/leasing_form_dialog.dart` — Add/Edit Property dialog (name, category, floor, status, contact/email/notes, area entries, and a Photos section that's only enabled after the unit has a real server-assigned id — new units must be saved once before photos can be added).
  - `presentation/widgets/unit_agreement_dialog.dart` (`UnitAgreementDialog`) — **unit-scoped**, takes `unitId` + `unitName` (not `tenantId`/`tenantName`). Shows extracted agreement fields (parties, area, financials, lease term, special clauses) and an admin-only upload flow (3-step: request signed URL → PUT to GCS → notify backend to extract). Also used from the tenants feature (tenant detail screen) passing the same unit id.
- **Domain entities**:
  - `domain/entities/leasing_unit.dart` — `LeasingUnit` (id, name, companyName, category, floor, status, areas: `List<AreaEntry>`, contact, email, notes, photos: `List<String>`) + `AreaEntry` (type: covered/open/common, sqft, rate → derived `rent`). Has `mockList` (11 hardcoded Bogineni properties) unused by the live app except as sample/reference data — `LeasingRepository.getAll()` no longer falls back to it (falls back to `[]` on error).
  - `domain/entities/unit_agreement.dart` — `UnitAgreement`, keyed by `unitId` (see Known Issues item confirming this is intentional, not a leftover).
- **Legacy/dead code**:
  - `domain/entities/property.dart` (`Property`, `Unit`), `data/repositories/property_repository.dart` (`PropertyRepository`), `presentation/providers/properties_provider.dart` (`PropertiesProvider`), `presentation/screens/property_list_screen.dart`, `presentation/screens/property_detail_screen.dart` — **none of these are reachable via `app_router.dart`**. Only `LeasingListScreen` is routed (`/properties`). `PropertyRepository` calls `/api/v1/properties*` endpoints that **do not exist** in the backend (`backend/main.py` has no such `include_router`) — confirmed dead/broken if ever invoked.
  - `PropertiesProvider` IS still registered as a `ChangeNotifierProvider` in `frontend/lib/main.dart:38`, but nothing consumes it since no route builds `PropertyListScreen`/`PropertyDetailScreen`. This looks like an earlier prototype (mock Property/Unit model with US-style address fields) superseded by the India-specific `LeasingUnit` model, with cleanup of `main.dart` never finished.

## Backend
- Router: `backend/routers/leasing.py`, mounted at `/api/v1/leasing` (see `backend/main.py:53`).
- Key endpoints:
  - `GET /` , `GET /{unit_id}` , `POST /` , `PUT /{unit_id}` , `DELETE /{unit_id}` — CRUD for `leasing_units` + `area_entries` (backend-side CRUD exists but the frontend repository bypasses it, calling Supabase directly instead — this router path appears to be unused by `LeasingListScreen`/`LeasingRepository`).
  - `POST /{unit_id}/photos`, `DELETE /{unit_id}/photos` — multipart upload/delete for a single photo; appends/removes from `leasing_units.photos`. Goes straight through the backend (no signed-URL step), 10 MB/photo limit, public bucket.
  - `POST /{unit_id}/agreement/upload-url` → `POST /{unit_id}/agreement/from-storage` — two-step signed-URL upload for lease agreements (see GCS pattern below).
  - `GET /{unit_id}/agreement` — returns extracted `unit_agreements` row for the unit, 404 if none.
  - `GET /{unit_id}/agreement/download` — **download-proxy pattern confirmed**: streams the original file bytes back through the backend (reads `storage_path` from `unit_agreements`, downloads from GCS server-side, returns as `Response`) instead of exposing a raw/signed GCS URL. Frontend's "View original document" link in `unit_agreement_dialog.dart` calls this endpoint directly (`launchUrlString('${ApiConfig.baseUrl}/api/v1/leasing/$unitId/agreement/download')`), not the stored `file_url`.
  - `POST /import-pdf` — accepts a Leasing Area Statement PDF/image, sends it to Claude (`model="claude-opus-4-8"`) with a prompt to extract every unit as JSON (name, company_name, category, floor, status, areas[]); returns the parsed array (not yet persisted — frontend confirms via preview dialog then calls `LeasingProvider.addImported`).
  - `GET /summary/occupancy` — aggregate counts by status.
- GCS pattern (`backend/gcs.py`):
  - **Two buckets**: `GCS_BUCKET` (private — lease/tenant documents, PII) accessed only via short-lived v4 signed URLs; `GCS_PUBLIC_BUCKET` (public — property/unit photos) with stable non-expiring URLs (`allUsers` read at bucket level).
  - **Signed-URL upload flow** (agreements only): Cloud Run has a hard ~32 MB inbound request-body limit that cannot be raised via config, so large agreement files (up to 100 MB) never hit Cloud Run directly. Flow: (1) `POST .../agreement/upload-url` → backend returns a signed PUT URL + `storage_path`; (2) browser `PUT`s file bytes straight to GCS; (3) `POST .../agreement/from-storage` → backend does an *outbound* GCS download (not subject to the inbound limit), runs Claude extraction, saves to `unit_agreements`.
  - **Photos use a different, simpler path**: multipart upload straight through the FastAPI endpoint (`/api/v1/leasing/{unit_id}/photos`) since photos are capped at 10 MB and go to the public bucket — no signed-URL indirection needed.
  - Object path convention: `org_{org_id}/properties/{property_id}/{category}/{uuid}_{filename}` (or `org_{org_id}/general/{category}/...` when no property).

## Database
- Tables:
  - `leasing_units` (`001_initial_schema.sql`, extended by `004_organizations.sql`/`006`/`007`): id (text PK), name, company_name, category, floor, status, contact, email, notes, `org_id` (uuid, added 004, auto-defaulted by trigger from 006), `photos text[] default '{}'` (added 007 — confirmed NOT a separate table).
  - `area_entries`: id (uuid), leasing_unit_id (text FK → leasing_units, cascade delete), type, sqft, rate.
  - `unit_agreements` (`005_unit_agreements.sql`): `unit_id text not null unique references leasing_units(id)` — **confirmed unique-per-unit, upsert semantics** (one agreement per property, replacing on re-upload), NOT tenant-scoped. Full set of extracted fields (parties, area, financials, amenities, lease term, GST, special_clauses jsonb, raw_extraction jsonb) plus `storage_path`/`file_url`/`org_id`.
  - `organizations`, `organization_members` (`004_organizations.sql`).
- Multi-tenancy: `organizations` (id, name) + `organization_members` (org_id, user_id, role — admin/manager/viewer, unique per org+user). `leasing_units.org_id` and `documents.org_id` link records to an org; `006_backfill_org_id.sql` added a `set_default_org_id()` `BEFORE INSERT` trigger on both tables so every new row (regardless of insert path — direct Supabase from Flutter, backend routes, PDF/Excel import) auto-fills `org_id` from the oldest existing org if omitted. GCS paths are scoped by `org_id` (`org_{org_id}/properties/{property_id}/...`), so a missing `org_id` is what silently breaks photo/agreement uploads for a unit (`leasing.py` raises 400 "no organization set" in that case).

## Key patterns / architecture notes
- Frontend reads/writes `leasing_units`/`area_entries` directly via the Supabase client (`LeasingRepository`), bypassing the backend's own CRUD endpoints in `leasing.py` for that data — the backend router's CRUD (`GET/POST/PUT/DELETE /api/v1/leasing/...` base paths) exists but appears unused by the current frontend.
- "Portfolio"/"company" is a plain string label (`LeasingUnit.companyName`, default `'Bogineni Black'`), not a foreign key to any table — units are grouped client-side in `LeasingProvider.companies` by exact string match. Bulk import (Excel via `parseExcelBytes` or PDF via `/api/v1/leasing/import-pdf`) tags every parsed unit with a single `companyName` derived from the source filename (or from Claude's extracted `company_name` header field for PDFs), so "importing a portfolio" = one file → one company/portfolio label → N units.
- Status set is exactly 4 values everywhere (`LeasingUnit.statuses`): `occupied`, `vacant`, `in_house`, `owner_occupied`. Only one non-properties-feature call site auto-flips status: `frontend/lib/features/tenants/presentation/widgets/tenant_form_dialog.dart:81` does `lp.update(unit.copyWith(status: 'occupied'))` when a tenant is added to a unit (grepped `copyWith(status:` across all of `frontend/lib` — this is the only match).
- Row actions in `leasing_list_screen.dart` (`_UnitRow`/`_UnitCardList`) — all 5 are wired: Publish to platforms (`onPublish`, enabled only when `status == 'vacant'`), Generate Invoice (`onGenerateInvoice`, enabled only when `status` is `occupied`/`in_house`), **Agreement Details is present** (`onViewAgreement` → `_viewAgreement` → `UnitAgreementDialog.show`), Edit, Delete.
- Agreement extraction model: `claude-sonnet-4-6` (`backend/agents/document_extractor.py`). PDF-import (bulk unit parsing) uses a different model string, `claude-opus-4-8` (`backend/routers/leasing.py:475`) — worth double-checking both model ids are current/correct if either extraction starts failing.

## Known Issues
- **`unit_agreements` is unit-scoped, matching the current backend/frontend code** — verified via `unit_agreement_dialog.dart` (`unitId`/`unitName` params, calls `/api/v1/leasing/{unitId}/agreement*`), `leasing.py` (`/{unit_id}/agreement/...` routes, upsert keyed by `unit_id`), and `005_unit_agreements.sql` (`unit_id text not null unique`). **No `010_*.sql` migration file exists** and no tenant-scoped agreement code was found anywhere — so despite the project's history of churn/reverts, this particular piece is currently consistent end-to-end, not a half-finished migration. (Re-verify if agreement-related bugs are reported, since this file predicted such drift as a real risk pattern in this codebase.)
- Dead/legacy `Property`/`Unit` domain model and its provider/repository/screens (see Frontend → Legacy/dead code) are still present in the tree and `PropertiesProvider` is still instantiated in `main.dart`, but not reachable through any route. Low risk of accidental use, but likely safe to delete in a cleanup pass — confirm with whoever owns the branch before removing.
- `leasing.py`'s base CRUD endpoints (`GET/POST/PUT/DELETE /api/v1/leasing/` and `/{unit_id}`) don't appear to be called by the current frontend (which uses Supabase directly for that data) — worth confirming whether anything else (e.g. a script, another client) still depends on them before assuming they're safe to remove.
- Two differently-named model strings are hardcoded for Claude calls in this feature (`claude-sonnet-4-6` for agreement extraction, `claude-opus-4-8` for PDF unit import) — no shared constant; if Anthropic model ids need to be bumped, both call sites must be updated separately.
